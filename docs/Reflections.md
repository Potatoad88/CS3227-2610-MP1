# Reflections on AI-Assisted Software Engineering

## 1. Reviewing Scope Before Implementation

**Prompt:** I asked the LLM to review my proposed food-place app and three UI screenshots which I created with Google Stitch, discuss strengths, risks, scope, and architecture, and evaluate Google Maps integration before writing code.

I formulated the prompt in two stages: product review first and implementation later. This prevented a visually attractive screenshot from silently becoming the specification and forced the LLM to consider whether every shown feature belonged in MP1. The most important assumption it made was that Google Maps would require API-key management, billing configuration, network access, and more failure handling than a peer-tested desktop release needed. That assumption was sensible, but “Maps is valuable” and “Maps belongs in the first release” are different claims.

I verified the recommendation against the assignment's emphasis on a complete personal utility app and software engineering practice. CRUD, filtering, random selection, persistence, validation, and documentation already formed a coherent workflow. I therefore kept manually entered distance but deferred geocoding and route calculations. The engineering judgement was deciding that reliability and testability were more valuable than another external integration. Next time I would state an explicit time budget and acceptance criteria in the first prompt so scope advice can be tied to measurable constraints.

## 2. Requesting a JavaFX and Gradle Implementation

**Prompt:** After agreeing to defer Maps, I asked the LLM to implement the Java desktop app with JavaFX and Gradle, based on the landing, saved-list, and add/edit screenshots.

The prompt named both the technology and the visible screens while leaving internal structure open. The LLM assumed a layered `ui`, `logic`, `model`, and `storage` design and chose JSON for local persistence. This was useful because the logic could be tested without starting JavaFX. However, the first launcher assumed that either `gradlew` or a global Gradle installation already existed. That was wrong in my environment: both `./gradlew run` and `gradle run` initially failed.

The prompt evolved after observing the real environment. I reported the exact terminal errors instead of simply saying that the app did not run. The launcher was first made project-local and was later replaced with the official Gradle wrapper, including `gradlew.bat`, when I decided to support Windows source launches. I verified the setup by compiling, testing, and launching through the wrapper rather than trusting the generated configuration. GitHub Actions then exercised the native wrapper commands on Ubuntu and Windows. Manual screenshot checks also exposed visual issues such as low input contrast, truncated dialog text, and inconsistent button corners. This showed that compilation verifies structure, not usability. Next time I would include “fresh-machine setup with no global Gradle,” supported operating systems, and minimum-window visual checks in the initial acceptance criteria.

## 3. Simplification, Favourite Removal, and Stable IDs

**Prompts:** I invoked Ponytail full to clean up the project, then asked to remove the favourite flag completely. After an update caused a null-ID exception, I reported the stack-trace message and asked whether place names should become IDs.

The cleanup prompt intentionally asked the LLM to look for unnecessary code rather than add features. It removed favourite-related state that had no user workflow and reduced stale model, JSON, CSS, and test behavior. The later exception showed a risk of broad AI refactoring: older saved records could still have missing IDs even though new objects generated UUIDs. The model had assumed loaded data always satisfied the latest schema.

I supplied the exact exception instead of asking for a generic fix. The correction was placed in the `FoodPlace` constructor so every construction path regenerates a missing or blank ID. I rejected names as IDs because duplicate restaurant names are legitimate and names can change during editing. UUIDs separate identity from editable display data. I verified the fix through update/reload tests and by checking that a place constructed without an ID receives one before persistence. The lesson is that simplification still requires migration thinking: deleting a feature from source code does not automatically remove older states from persisted data.

## 4. Investigating a Failed Dependency Update

**Prompts:** After adding GitHub Actions, CodeQL, and Dependabot, I showed the LLM three dependency-update pull requests and asked whether I should merge them. When the JUnit update failed, I supplied the complete Gradle Actions output and later asked how to add the required launcher dependency.

I deliberately asked for an explanation before merging because a Dependabot pull request being automated does not make it automatically correct. The LLM distinguished the two green GitHub Actions updates from the failing JUnit major-version update. It explained that `actions/checkout` obtains the repository for a workflow and `actions/setup-java` provides the selected Java runtime, while the JUnit BOM controls a group of related test-library versions. This made the review decision about each pull request specific rather than treating all three as equivalent maintenance.

The initial CI output only said that tests had failed, so the LLM could not safely identify the cause from that summary alone. The prompt evolved by including the exact task output and reproducing the dependency change locally. The investigation found that JUnit 6 needed an explicit `junit-platform-launcher` runtime dependency with the project's Gradle setup. I verified the proposed correction by running all nine tests on the update branch and waiting for the GitHub checks to pass before merging. The engineering judgement was deciding not to bypass or dismiss a failed check merely because the application code had not changed.

This example also showed a limit of automation. Dependabot detected that a newer version existed, but it could not decide whether the major upgrade was appropriate for the project or explain the compatibility failure in the context of my build. The LLM accelerated diagnosis, while I still had to review the version change, require evidence from the test suite, and choose when to merge. Next time I would inspect release notes for major updates before attempting the merge and ask the LLM to identify likely breaking changes from those notes first.

## Overall Reflection

Prompting was most effective for exploring scope, generating a complete vertical slice, tracing behavior across layers, and interpreting concrete failure output. It was less effective for visual polish and environment-specific setup, where screenshots, terminal output, and manual observation were more reliable than abstract prompts. Broad prompts were useful early for discovering options, but focused prompts containing an invariant, stack trace, screenshot, or failed command produced more verifiable changes. In particular, expressing requirements as behavioural invariants, such as requiring the random picker's candidate set to match the filtered list, made them easier to translate into tests.

The LLM accelerated implementation, but it did not replace engineering judgement. I still had to choose release scope, reject name-based identity, decide what belonged in automated versus manual testing, review dependency updates, inspect persistence compatibility, and keep documentation synchronized with the product. I also learned that verification must match the type of change: JUnit tests for domain logic, storage round trips for persistence, CI for operating-system and dependency setup, and manual launches for JavaFX appearance and interaction.

In future AI-assisted projects, I would define acceptance tests and supported environments earlier, submit smaller change requests, and ask the model to state migration and failure-mode assumptions before editing persistent data or build configuration. I would also keep a short record of the original prompt, the AI's assumptions, my verification evidence, and the final decision as each significant change is completed instead of reconstructing that reasoning near the end.

A late assignment update provided a useful final example of this process. Java SE 25, three-operating-system support, and bundled JavaFX release JARs changed the build requirements after the application itself was complete. The LLM helped identify the minimum compatible Gradle version and the need for platform-specific JavaFX native libraries, but I still had to decide what “cross-platform” could honestly mean. I chose four explicit JARs and CI jobs instead of claiming that one native JAR would work everywhere. This kept the submission testable while avoiding the much larger scope of installers and bundled JDKs.
