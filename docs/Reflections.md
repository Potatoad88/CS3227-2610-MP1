# Reflections on AI-Assisted Software Engineering

## 1. Reviewing Scope Before Implementation

**Prompt:** I asked the LLM to review my proposed food-place app and three UI screenshots which I created with Google Stitch, discuss strengths, risks, scope, and architecture, and evaluate Google Maps integration before writing code.

I formulated the prompt in two stages: product review first and implementation later. This prevented a visually attractive screenshot from silently becoming the specification and forced the LLM to consider whether every shown feature belonged in MP1. The most important assumption it made was that Google Maps would require API-key management, billing configuration, network access, and more failure handling than a peer-tested desktop release needed. That assumption was sensible, but “Maps is valuable” and “Maps belongs in the first release” are different claims.

I verified the recommendation against the assignment's emphasis on a complete personal utility app and software engineering practice. CRUD, filtering, random selection, persistence, validation, and documentation already formed a coherent workflow. I therefore kept manually entered distance but deferred geocoding and route calculations. The engineering judgement was deciding that reliability and testability were more valuable than another external integration. Next time I would state an explicit time budget and acceptance criteria in the first prompt so scope advice can be tied to measurable constraints.

## 2. Refining Build Setup and UI Through Verification

**Prompt:** After agreeing to defer Maps, I asked, "Feel free to use JavaFX and Gradle to make the project better," while retaining the landing, saved-list, and add/edit screenshots as the visual reference.

The prompt named both the technology and the visible screens while leaving internal structure open. The LLM assumed a layered `ui`, `logic`, `model`, and `storage` design and chose JSON for local persistence. This was useful because the logic could be tested without starting JavaFX. However, the first launcher assumed that either `gradlew` or a global Gradle installation already existed. That was wrong in my environment: both `./gradlew run` and `gradle run` initially failed.

The prompt evolved after observing the real environment. I reported the exact errors, "`zsh: no such file or directory: ./gradlew`" and "`zsh: command not found: gradle`," instead of simply saying that the app did not run. The launcher was first made project-local and was later replaced with the official Gradle wrapper, including `gradlew.bat`, when I decided to support Windows source launches. I verified the setup by compiling, testing, and launching through the wrapper rather than trusting the generated configuration. GitHub Actions then exercised the native wrapper commands on Ubuntu and Windows.

The screenshots also changed how I prompted for UI corrections. Broad requests such as improving dark mode were less useful than identifying the exact component, visible defect, and intended result. For example, I supplied screenshots showing the bright choice-box popup, the extra rectangle inside the notes field, and text ending in an ellipsis, then asked for each control to match its surrounding theme and wrap where appropriate. I verified these changes manually in both themes and at smaller window sizes because compilation and logic tests cannot establish visual consistency. This showed that compilation verifies structure, not usability. Next time I would include "fresh-machine setup with no global Gradle," supported operating systems, and minimum-window visual checks in the initial acceptance criteria.

## 3. Resolving Identity and Persistence Assumptions

**Prompt:** After an update caused a null-ID exception, I reported the exact stack-trace message and asked whether restaurant names should be used as IDs to prevent duplicate places.

The exception exposed an assumption that every loaded place already satisfied the latest model requirements. New objects generated UUIDs, but persisted records created under an earlier version could still have missing IDs. This showed that changing a model is not only a source-code concern; existing stored data must also be considered.

I supplied the exact exception instead of asking for a generic fix. The correction was placed in the `FoodPlace` constructor so every construction path regenerates a missing or blank ID. I rejected names as IDs because duplicate restaurant names are legitimate and names can change during editing. UUIDs separate identity from editable display data. I verified the fix through update/reload tests and by checking that a place constructed without an ID receives one before persistence. The lesson is that model changes require migration thinking: updating source code does not automatically update previously persisted data.

## 4. Investigating a Failed Dependency Update

**Prompts:** After adding GitHub Actions, CodeQL, and Dependabot, I showed the LLM three dependency-update pull requests and asked whether I should merge them. When the JUnit update failed, I supplied the complete Gradle Actions output and later asked how to add the required launcher dependency.

I deliberately asked for an explanation before merging because a Dependabot pull request being automated does not make it automatically correct. The LLM distinguished the two green GitHub Actions updates from the failing JUnit major-version update. It explained that `actions/checkout` obtains the repository for a workflow and `actions/setup-java` provides the selected Java runtime, while the JUnit BOM controls a group of related test-library versions. This made the review decision about each pull request specific rather than treating all three as equivalent maintenance.

The initial CI output only said that tests had failed, so the LLM could not safely identify the cause from that summary alone. The prompt evolved by including the exact task output and reproducing the dependency change locally. The investigation found that JUnit 6 needed an explicit `junit-platform-launcher` runtime dependency with the project's Gradle setup. I verified the proposed correction by running all nine tests that existed at that stage on the update branch and waiting for the GitHub checks to pass before merging. The engineering judgement was deciding not to bypass or dismiss a failed check merely because the application code had not changed.

This example also showed a limit of automation. Dependabot detected that a newer version existed, but it could not decide whether the major upgrade was appropriate for the project or explain the compatibility failure in the context of my build. The LLM accelerated diagnosis, while I still had to review the version change, require evidence from the test suite, and choose when to merge. Next time I would inspect release notes for major updates before attempting the merge and ask the LLM to identify likely breaking changes from those notes first.

## 5. Using an Examiner-Style Audit to Challenge Release Assumptions

**Prompts:** Near the end of development, I asked the LLM to act as an examiner, inspect the complete repository, run the build and application where possible, and report logic, UI, storage, release, and documentation bugs. I then asked it to compare the Gradle and JavaFX packaging with my earlier CS2103T iP and reconsider whether one universal JAR would be better than four platform-specific JARs.

I formulated the first prompt broadly because I wanted an independent release review rather than confirmation of one suspected defect. This exposed an important limitation in an earlier claim: save-before-mutate ordering protected the manager's in-memory list when `save()` threw, but the direct `Files.writeString()` call could still truncate the existing JSON file before an interrupted write completed. The original tests simulated a storage method that failed before touching the file, so they verified the manager invariant without verifying file replacement safety. I refined the prompt after understanding this distinction and requested a temporary-file implementation. The resulting storage code writes a complete sibling file before replacing the original, prefers an atomic move when supported, cleans up temporary files, and has a focused replacement test.

The packaging comparison challenged a different assumption: one JAR seemed more user-friendly because my iP used the Shadow plugin to bundle Windows, Linux, and macOS JavaFX libraries together. Instead of copying that build mechanically, I asked the LLM to inspect the actual native files. The evidence showed that the iP contained only x64 libraries, while this project also needed Apple silicon support. Intel and ARM JavaFX libraries use identical resource names such as `libglass.dylib`, so placing both directly in one fat JAR would cause collisions. I therefore retained four explicit artifacts rather than introducing a custom bootstrap process merely to produce one download.

This investigation also corrected my mental model of compatibility. I initially expected an Apple silicon processor to always require the ARM64 JAR, but my installed JDK was an x64 build running through Rosetta. JavaFX native libraries must match both the operating system and the architecture of the active JDK process. I verified this using Java's `os.arch` property and by inspecting the packaged native libraries, then updated the setup instructions to use the reported JDK architecture instead of only the physical processor.

A later storage discussion extended the same audit. My initial suggestion was to reset a malformed `places.json` file to an empty list and warn the user. The LLM identified that overwriting the malformed file would silently destroy the only copy of potentially recoverable data. I refined the requirement to preserve the original content in a timestamped backup, reset only the active file, and show the backup path in a wrapping startup dialog. This was a better outcome than either crashing indefinitely or pretending recovery was harmless. It also required engineering judgement about the failure boundary: the app may continue only after the backup and reset both succeed; otherwise the error must still propagate rather than risk data loss.

The recovery test produced another useful lesson. The important contract was that the malformed bytes were preserved, the active storage became a valid empty list, and a subsequent load succeeded. Exact whitespace in the regenerated JSON was not part of that behavior. I therefore treated observable recovery and data preservation as the test contract instead of coupling the test to one insignificant serialization layout. This made the test more resistant to harmless formatting changes while still protecting the failure mode that mattered.

Prompting was useful for tracing risks across build, storage, and documentation, but manual engineering judgement was still required to decide which findings justified changes. I accepted the small storage reliability fix and clearer architecture instructions, but rejected a custom class-loading launcher because its complexity and new failure modes outweighed the convenience of one JAR. I verified the final changes with a new JUnit scenario, the complete Gradle `clean check` lifecycle, Checkstyle, rebuilt release JARs, and documentation comparison. Next time I would include durability of the on-disk file and runtime architecture in the initial acceptance criteria, and I would ask tests to distinguish in-memory consistency from persistent-file integrity explicitly.

## Overall Reflection

**Why I formulated prompts this way:** I tried to provide enough context for the LLM to understand the problem, existing code, constraints, and desired outcome while leaving genuine design decisions open for discussion. For substantial changes, I used plan mode first so the LLM could inspect the repository, explain its assumptions, and propose an approach before implementation. This gave me an opportunity to clarify requirements and verify the design before allowing code changes.

**Assumptions made by the LLM:** The LLM sometimes assumed that the development environment or persisted data already matched the latest project design. The initial setup assumed that Gradle or a working wrapper was available, while my machine had neither. A later refactoring assumed that every saved place had a valid UUID even though older records could have missing IDs. Release work also required further investigation to distinguish the physical Mac processor from the architecture of the active JDK. These cases showed that environment, migration, and compatibility assumptions should be stated and verified explicitly.

**What the LLM got wrong:** Most discovered issues were visual rather than fundamental logic errors. These included insufficient contrast, inconsistent button outlines, bright dropdown menus in dark mode, nested backgrounds in the notes field, truncated text, and controls that did not wrap correctly in smaller windows. There were also non-visual problems, including the initial missing wrapper, a null-ID update failure, and storage code that protected in-memory state without initially guaranteeing safe replacement of the existing file. Generated code therefore still required both visual inspection and technical review.

**How I verified results:** I read through generated code and asked the LLM to explain unfamiliar sections rather than accepting them without understanding. I ran the complete JUnit and Checkstyle checks, inspected CI results, launched the release JARs, and manually tested the main workflows. My end-to-end checks covered adding, viewing, editing, deleting, searching, filtering, random selection, restart persistence, malformed-storage recovery, dark mode, and smaller window sizes. Verification had to match the type of change: JUnit for domain logic, round trips and replacement checks for storage, artifact inspection and CI for build compatibility, and manual launches for JavaFX appearance and interaction.

**How prompts evolved:** Prompts became narrower and more evidence-based as development progressed. An initial prompt might request a broad feature or review, while follow-up prompts included an exact stack trace, terminal error, screenshot, failed test, or behavioural invariant. For example, "improve dark mode" became requests identifying the affected control, its incorrect appearance, and the desired contrast or border behaviour. A generic update failure became an investigation of the exact null-ID exception. Expressing requirements as observable invariants, such as requiring the random picker's candidate set to match the filtered list, also made them easier to translate into tests.

**When prompting was less effective than manual work:** Prompting was less effective for discovering visual defects and judging whether the interface felt consistent. The code could compile and pass tests even when controls had poor contrast, truncated text, or mismatched borders. Manual testing was also necessary for keyboard and mouse interactions, dialog behaviour, responsive layout, theme persistence, and launching platform-specific JARs. The LLM helped diagnose these problems after I supplied evidence, but direct observation was usually required to discover them.

**Engineering judgement that remained necessary:** I still had to decide which features belonged within the assignment scope and which introduced unnecessary complexity. I deferred Google Maps because API keys, billing, network failures, and geocoding increased risk without sufficiently strengthening the core workflow. I selected UUIDs instead of restaurant names as IDs because names are editable and duplicates are valid. I retained four platform-specific JARs instead of introducing a complicated universal launcher, preserved malformed storage before resetting it, and required random selection to use exactly the applied search and filters. I also had to distinguish worthwhile regression tests from tests added only to increase their count and decide which behaviours required automated versus manual verification.

**What I would do differently next time:** I would define supported environments, acceptance criteria, persistence behaviour, and manual test scenarios earlier. I would ask the LLM to state its assumptions about existing data, migration, operating systems, and failure handling before implementation. I would divide large changes into smaller checkpoints, verify each checkpoint before continuing, and include visual criteria such as light and dark mode, text wrapping, and minimum-window behaviour from the beginning. I would also record important prompts, assumptions, verification evidence, and decisions as they occur instead of reconstructing them near the end. The summary logs and focused Git commits helped with traceability, but AI-generated summaries still required manual checking against the actual code, commands, and decisions.
